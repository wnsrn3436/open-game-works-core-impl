# update core: iap must-fix M1

## done

- Module `iap` (server), must-fix M1. `bind_tokenless` (`server/core/iap/grant.ts:635`) now returns false when the binding is absent and the receipt is not a device receipt, so `judge` gives `INVALID` and no binding is written. The case where the binding already belongs to the requesting user is unchanged and comes before the new condition. Commit d3d5b75
- Two core tests added in `server/core/iap/tests/transfer.test.ts`
  - `VALID`, no account token, `device_receipt` false, no binding gives `INVALID` with no balance and no binding, on `APPLE` and `GOOGLE`. Another user then sends the same transaction with `device_receipt` true, is bound and gets `GRANTED`, and the payment record is `GRANTED` for that user. Run before the fix, this test failed on sqlite and postgresql (`GRANTED` where `INVALID` was expected). It passes after the fix
  - After a binding exists, a receipt with `device_receipt` false and the same original transaction ID gives `GRANTED` to the bound user and `OTHER_USER` to another user. This test guards the kept case and passed before the fix too, so it does not by itself show M1
- `ogw core test server` passed for `iap admin-api auth matchmaker notice rating routing testing` (the edited module and the server modules of `ogw core dependents iap`). `ogw code check core` passed: type check, lint, dependency, secret
- No engine-specific implementation rules document was written, and `## <engine> build` of `tools/ogw.md` was not written. Neither was a target

## spec proposals

The lead agent has to make these in `skills/server-core/modules/iap.md`. It was not edited.

1. `## test` needs one new line, because no line checks the new condition. Proposed text: "When a user sends a `VALID` store transaction without an account token, with no binding of its original transaction ID, and with a receipt that is not a device receipt, it gives `INVALID`, grants nothing and leaves no binding. When a user then sends it with a device receipt within purchase time + `iap.withdrawnRecordRetentionMs`, it binds the original transaction ID to that user and gives `GRANTED`. When the binding belongs to the requesting user, a receipt that is not a device receipt continues"
2. The existing `## test` lines stay correct and need no edit. Line 421 (first sender of a `GOOGLE` store transaction without an account token gets `GRANTED`) holds because every `iap-google` receipt is a device receipt, and the bound-user sentence of that line holds. Line 422 (concurrent senders) and line 455 (deleted store transaction gives `INVALID`) run with the fake adapter's default device receipt and pass
3. Optional, for the human to decide: `## error` has no row for the `INVALID` of a store transaction without an account token, so an attempt rejected by this condition leaves only an `INVALID` payment record and no `security` log, while the other rejections of another user's transaction do leave one. A row with a `security` log and a `cause` would make these attempts visible. No log was added, because the spec does not state one

## unverified

- The real `iap-apple` adapter was not run through this path. The fix was run with the fake adapter's `device_receipt` value. That `iap-apple` reports a decimal transaction ID receipt as not a device receipt comes from reading `server/core/iap/adapters/apple.ts` and from its existing adapter test
- The client plugin `ogw-iap-apple` is not in `client/godot/plugins/` yet, so what it sends as receipt data could not be checked. `iap.md` allows both a signed JWS and a decimal transaction ID for Apple. After this fix, a buyer of an Apple store transaction without an account token (e.g. offer code redemption) gets `INVALID` if the plugin sends the decimal form, and `INVALID` ends the store transaction (`iap.md:62`). The plugin has to send the signed JWS. `payment-core.md` and `engines/godot.md` do not state this, so it is worth writing there when that plugin is made
- How easily an attacker can learn a transaction ID was not measured, as the must-fix record also says
- `ogw core test` ran on the `server` target only, as the edited side. The client modules that `ogw core dependents iap` lists were not run. The lead agent does the run over all modules
