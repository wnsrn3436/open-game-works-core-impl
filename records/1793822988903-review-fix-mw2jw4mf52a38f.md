# review fix: migration round 1

## done

- Module `migration` (server). `convert` (server/core/migration/index.ts:223-249) now encodes the converted item inside a try. When the encode throws, it returns `failed` with the from version of the last converter it applied. So `convert_logged` writes the `item conversion failed` error log, `convert_item` gives `FAILED` (the request is `INTERNAL` and the item is unchanged), and `migrate_record` gives `FAILED` for that record instead of throwing out of `migrate_snapshot`.
- Added core tests in `server/core/migration/tests/`: 2 in `convert.test.ts`, 3 in `batch.test.ts` and 1 in `snapshot.test.ts`.
- Last `ogw core test server migration routing testing` (migration and the modules `ogw core dependents migration` lists): every module passed on SQLite and PostgreSQL. Last `ogw code check core`: type check, lint, dependency and secret all passed.
- No engine-specific implementation rules document was written, and `## <engine> build` of `tools/ogw.md` was not written.

## review

- R1-1: fixed. server/core/migration/index.ts:225 (`applied` keeps the from version of the last applied converter) and :244-248 (encode in a try, `failed` on a throw).
  - Test convert.test.ts:112 `a converter result that cannot be encoded is FAILED: ...`: the `QuestUserState:2` converter sets `progress` to the number `1`. For a version 1 item and a version 2 item it checks that the request rejects, the row bytes and version are unchanged, and the log has `item_id` `41`, the stored version and `from_version` `2`.
  - Test snapshot.test.ts:87 `a record whose converter result cannot be encoded is FAILED, ...`: `migrate_snapshot` gives that record `FAILED` with an error that starts `from version 2: the converter result cannot be encoded`, and gives the other record `OK`.
  - Both tests failed on the code before the fix: no log fields, and `TypeError: Cannot convert 1 to a BigInt` out of `migrate_snapshot`.
- R1-2: fixed. Test batch.test.ts:222 `failed_users keeps up to migration.maxRecordedFailures users, ...`: `maxRecordedFailures` 2, 4 of 5 users fail. It checks that `failed_users` holds the 2 smallest user IDs, `failed_count` is 4 and there are 4 failure logs. With `if (out.length >= max) break;` removed, the test fails on SQLite and PostgreSQL.
- R1-3: fixed. Test batch.test.ts:232 `a user the step picked who is withdrawn before its user transaction ...`: the user is withdrawn with `delete_user` after the scan and right before the step's user transaction. It checks that `run_user_transaction` gives `WITHDRAWN`, `converted_users` is 2, `failed_count` is 0, `failed_users` is `[]`, there is no failure log, and the batch ends `DONE`. With `else if (result !== 'WITHDRAWN')` changed to `else`, the test fails on SQLite and PostgreSQL.
- R1-4: fixed. Test convert.test.ts:132 `stored bytes that are not a message of the kind are FAILED: ...`: it seeds `ff ff ff` at version 1 and checks that the request rejects, the row is unchanged, and there is one `item conversion failed` log with `item_kind`, `item_id`, `stored_version`, `from_version` and `error`. With the decode failure branch changed to return the stored bytes, the test fails on SQLite and PostgreSQL.
- R1-5: fixed. Test batch.test.ts:265 `a step with no user to pick that loses its lease to another server instance before its DONE write leaves status RUNNING`: after the step's scan and before its DONE write, the test writes a new `lease_owner` and `lease_until_at` to the batch record, as the lease write of another server instance does. It checks that `status` stays `RUNNING`, the other instance's lease is unchanged, and there is one `warn` lease-lost log. With `lease_owner = $3` of `MARK_DONE` replaced by `$3 = $3`, the test fails on SQLite and PostgreSQL.

## unverified
