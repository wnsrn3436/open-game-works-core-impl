## done

- `CutsceneCore` (Godot): `client/godot/core/cutscene_core/cutscene_core.gd`
  - The auto advance wait is no longer restarted when auto advance is turned on. `_auto_from_ms` is set only at `Line` start and on line history close (`cutscene-core.md:122`, `:165`)
  - Tween presets of `Move`, `Camera`, `ScreenEffect` are got with `ResourceCore.get_loaded`(key, `TweenCore.get_preset_kind()`, playback scope) at command start (`cutscene-core.md:76`). Each command gets the preset once and passes it to the start check and to `copy_definition` / `play_preset`

## spec proposals

- R1-2: add `InputCore.maxKeysPerAction` (integer, core, content, "maximum number of keys and mouse buttons in the key binding of one action; sizes the buffer of `InputCore.get_keys` in the advance input check") and `InputCore.maxPadButtonsPerAction` (integer, core, content, same for `InputCore.get_pad_buttons`) to `## settings` of `cutscene-core.md`. This is the same pattern as the existing `TweenCore.maxDurationMs` row. After that change, CutsceneCore would read both keys in `init` and size one buffer there, not read them on each advance button click. Another way is a new `InputCore` operation that says whether an input event is in the binding of an action. That would also be a spec change, in `input-core.md`

## review

- R1-1: fixed. `client/godot/core/cutscene_core/cutscene_core.gd:1675` (`_on_auto_click` no longer sets `_auto_from_ms`); the comment at `:145` is updated. Added tests: `tests/test_line.gd:215` `test_auto_advance_turned_on_after_its_delay_ends_the_line_in_the_next_frame` (the run path from the finding: no voice, turned on 3 × the delay after `Line` start, the `Line` ends on the next frame without moving the clock) and `tests/test_line.gd:230` `test_auto_advance_turned_on_during_its_delay_ends_the_line_at_the_delay_from_voice_end` (turned on halfway through the delay after voice end, the `Line` ends at the delay measured from voice end)
- R1-2: disputed (not fixed in code). The finding is right that the module reads two keys that its `## settings` does not list. But the code-only fix it proposes ("size the buffer without reading another module's settings") cannot be done with the current spec:
  - `InputCore` has no operation that gives the binding count, or that says whether an event is in a binding (`input-core.md:25-58`)
  - When the buffer is smaller than the binding, `get_keys` and `get_pad_buttons` leave an error log (`input_core.gd:1769`, `godot.md:477`). So CutsceneCore cannot grow the buffer by trial
  - A key binding has no upper bound other than `InputCore.maxKeysPerAction`, because any key code that `OS.find_keycode_from_string` accepts is a key name (`input_core.gd:1651`). So there is no fixed size that does not need the key
  - The other fix in the finding (add the two keys to the spec `## settings`) is a spec change, and the input sets `spec change: no`. It is written in `## spec proposals`. The code is unchanged (`cutscene_core.gd:32`, `:33`, `:1650`), and it gives no wrong result today (the finding says the same)
- R1-3: fixed. `client/godot/core/cutscene_core/cutscene_core.gd:1027` (`_preset` uses `ResourceCore.get_loaded` with the playback scope), `:1042` (`_first_change_or_log` takes the preset), `:1076`, `:1139`, `:1164` (each command gets the preset once at command start), `:292` (step 3 skips tween items, which the preload already loaded with the playback scope). Added test: `tests/test_start_check.gd:300` `test_a_move_gets_its_tween_preset_with_get_loaded_at_command_start`. A `Move` whose preset did not load in step 3 runs after the tween fallback is swapped with the public `ResourceCore.register_kind` after step 3. With the step 3 result kept, it fails the start check
