| R3-1 | open | The spec change settles it. virtual-pad-core.md:97 says that when `Active`, the press of a pointer pressed in an element area is consumed "also when no element holds that pointer". It sets no limit, and the moves and release of a pointer are consumed only while an element holds it. A new test item (:218) requires that with `InputCore.maxJudgePointers` 50 and 40 pointers held in one button area, a `Fixed` joystick press at 0.5 times the radius gives `get_vector` (0.5, 0), and that the 40 releases give no `TapEvent`. The code did not change in the range: `_add_area_pointer` (virtual_pad_core.gd:530) still returns `false` once all 32 `_AREA_POINTER_SLOTS` (:41) are taken, and `_on_element_input` (:508) then neither accepts nor takes the press. A probe test of exactly that item, in a temporary clone of HEAD, failed with `[VECTOR2(0, 0)] expected to equal [VECTOR2(0.5, 0.0)]` and `[8] expected to equal [0]: no tap`. The joystick press (the 41st pointer) found no free entry, and pointers 33-40 became judge pointers and tapped. The spec change also removes the need to track pointers that no element holds, so the fix is: accept every press in an area while `ACTIVE`, and accept moves and releases only for `element.pointer_id`. The core test of :218 is missing |

## unknown

- The module code did not change in the commit range. Only `core-spec/VirtualPadCore.json` (the `InputCore.maxJudgePointers` settings key) changed, so this round compared the current code and tests with the parts of the definitions that the spec changes diff changed (virtual-pad-core.md `### pointer ownership`, settings and `## test`). The diff also changed input-core.md, ui-core.md and godot.md, but none of those changes concern VirtualPadCore except the input-core.md order of mouse input made from touch, which R4-1 uses
- Code that differs from the new rule but that I could not observe was not written as a finding. The code consumes the moves and release of an area pointer that no element holds (`_area_pointers.has`, virtual_pad_core.gd:512 and :519). The spec now says they are consumed only while an element holds the pointer. Such a pointer is not a judge pointer and touch is in no action binding, so a world stage that receives those inputs changes no result I could check. The fix of R3-1 removes this difference anyway
- `_on_element_input` accepts every `InputEventMouse` on an element while `ACTIVE` (:525), not only the left mouse button press made from touch and the inputs after it. A real mouse input switches the input device to `KeyboardMouse`, and so the pad to `HIDDEN`, before the UI stage. Mouse input made from touch never reaches the world stage. So I found no case where the extra accepting is observable. A real mouse hover with no device change was not checked on a device
- R4-1 was checked only for the `HIDDEN` path (`visible = false`). The `INACTIVE` path keeps the pad visible and only sets `mouse_filter` to `IGNORE`. I did not probe whether that keeps the engine mouse focus when the popup is not modal. A modal popup's blocker covers the UI below in any case
- Whether the engine touch focus (as opposed to the mouse focus) survives hiding was checked only by the probe's touch count of 0 in the R4-1 run
- Only the headless pass of `ogw core test godot VirtualPadCore --file` was run with the probe tests. The whole module suite, `--web`, the render pass, on-device touch and the QACore and BootstrapCore dependents were not run
