| R9-1 | spec | medium | client/godot/core/virtual_pad_core/virtual_pad_core.gd:560 | `_on_element_input` calls `_add_consumed(touch.index)` (:519) before `_press` (:520), which calls `InputCore.inject_action` (:592 for a button, through `_update_joystick` for a joystick). `_consumed_ids` is made with 16 slots in `init` (:113), and `_add_consumed` grows it with `_consumed_ids.resize(maxi(_CONSUMED_CAPACITY, _consumed_count * 2))` when it is full (:559-560). A `PackedInt64Array` growing from 16 to 32 items allocates a larger buffer. Run path: `open_layout(LAYOUT_FIXED)` in `Active`, press 16 touches (indices 0-15) in the `fire` area (the first one held by `fire`, the other 15 consumed with no element holding them, virtual-pad-core.md:95 and :97, all recorded in `_consumed_ids`), then press touch 16 at 0.5 times the radius to the right of the `stick` base center: `_add_consumed(16)` resizes `_consumed_ids` to 32 and then `_press` injects the direction actions, so memory is allocated between receiving that pointer and `InputCore.inject_action`, which open-game-works-core/skills/client-core/modules/virtual-pad-core.md:152 forbids. The spec contemplates this many pointers (the `## test` item at :218 holds 40 pointers in one button area while `InputCore.maxJudgePointers` is 50). `test_memory.gd` does not reach it: `_cycle` and `test_first_area_presses_after_open_allocate_nothing` press at most 2 pointer IDs at once, and `_cycle` never goes through `_on_input`, so the count stays at 1 | Do not grow the tracking on the pointer path: e.g. preallocate a capacity that covers every pointer that can be pressed at once (or record consumed pointers in a structure whose size is fixed at `init`), and add a `test_memory.gd` case that holds 16 or more consumed pointers and then presses a free element, measuring `MEMORY_STATIC` around that press | no | 85 |
| R9-2 | spec | medium | open-game-works-core/skills/client-core/modules/virtual-pad-core.md:226 | The second sentence of this `## test` item ("When the input device changes to `Gamepad` while a touch pressed in a button area is held, the elements become not visible UI elements when that touch is released") cannot hold under the other defining documents. The touch release is touch input, which device detection uses also when it is discarded (open-game-works-core/skills/client-core/modules/input-core.md:95, :114, :116; :352 shows a touch press switching `Gamepad` back to `Touch`), so the release makes the input device `Touch`, the state becomes `Active` (virtual-pad-core.md:117-122 with touch supported and no popup), and `Active` elements are drawn (virtual-pad-core.md:38), so they stay visible UI elements. The tests of this range show it: `client/godot/core/virtual_pad_core/tests/test_state.gd:103-113` (`test_elements_become_not_visible_when_the_held_touch_is_released`) has to call `InputCoreDev.set_test_device(GAMEPAD)` again after the release (comment at :110: "The release is touch input, so device detection makes the device `Touch` again") before it can assert that the elements are not visible, so no test checks the sentence as written, and none can. The core agent report (`records/1793891993706-review-fix-mw3oz52i626568.md`, `## spec proposals`) reaches the same conclusion | Reword the item so that the state stays `Hidden` through the release, e.g. the core agent's proposal: "When touch support is turned off with `set_test_touch_support(false)` while a touch pressed in a button area is held, the elements stay visible UI elements until that touch is released and are not visible UI elements after the release" (already checked by `test_state.gd::test_hidden_elements_become_not_visible_after_the_held_touch_is_released`) | yes | 85 |
