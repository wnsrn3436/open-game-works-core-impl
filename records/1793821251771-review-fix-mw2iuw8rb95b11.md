# SceneCore review fix round 1

## done

- `SceneCore` (Godot), commit `782e069`
  - R1-1: from stage 4 until stage 7, every node under the scene holder whose `process_mode` is not `PROCESS_MODE_INHERIT` or `PROCESS_MODE_DISABLED` is set to `PROCESS_MODE_DISABLED` and kept with its mode. This happens at four points: the stage 4 tree walk, `SceneTree.node_added`, a walk right after `on_preload` returns, and a walk in the core node's `_process` and `_physics_process`. At stage 7 the kept modes are given back, newest first, to the nodes that are still valid and still `PROCESS_MODE_DISABLED`; then the holder goes back to `PROCESS_MODE_INHERIT` (`client/godot/core/scene_core/scene_core.gd:320`, `:369`, `:633-656`, `:695-704`, `:722-729`, `client/godot/core/scene_core/scene_core_node.gd:6-12`)

## spec proposals

- `open-game-works-core/skills/client-core/engines/godot.md:291` (`SceneCore` scene holder row) has to describe the R1-1 step. The input gave no harness path, so this agent did not edit it. Proposed text to add after "...`AnimationPlayer` do not run.": "A node with a `process_mode` other than `PROCESS_MODE_INHERIT` does not inherit the holder, so from stage 4 until stage 7 each node under the holder whose `process_mode` is neither `PROCESS_MODE_INHERIT` nor `PROCESS_MODE_DISABLED` gets `PROCESS_MODE_DISABLED` and its mode is remembered. This is done on everything under the holder right after the `add_child()` of stage 4 and right after `on_preload` returns, on the nodes received with `SceneTree.node_added`, and at each `_process()` and `_physics_process()` of the SceneCore core node, which runs before the holder. Stage 7, before setting the holder to `PROCESS_MODE_INHERIT`, gives the remembered mode back, newest first, to each remembered node that is `is_instance_valid()` and still `PROCESS_MODE_DISABLED`."
- `scene-core.md` `### scene` does not say what happens when scene code changes the run state of one of its own nodes from stage 4 until before stage 7. This is the same gap as R1-2, for the per-frame side. Under the current mechanism, if scene code sets `PROCESS_MODE_DISABLED` on a node that SceneCore stopped, that node gets its remembered mode back at stage 7, because the two writes cannot be told apart. If scene code gives a node a mode of its own in the middle of a frame (e.g. after an `await` in `on_prepare` resumes), that node can run its callbacks once in the remaining part of that frame, before the next core node walk. Proposal: settle both cases together with R1-2. Either state that a scene-code change made from stage 4 until before stage 7 is kept at stage 7, or state that scene code does not change the visibility or run mode of its nodes from stage 4 until stage 7, outside `on_preload` and outside nodes it adds.
- R1-2: not fixed, because its `spec change` is `yes`

## unverified

- QACore on the native `godot` run: `skipped`, because the render pass did not run while the macOS screen was locked or the display was asleep. Its headless pass and the whole `--web` run passed
- Mid-frame mode changes (second item of `## spec proposals`): a node that scene code gives a mode of its own in the middle of a frame can run once in the rest of that frame. The tests do not cover this case. A scene node with a `process_priority` lower than the core node's can also run once before the per-frame walk; this was not tested either

The other real cause, "too many active blocks", was not reproduced: it needs 2^20 active blocks
