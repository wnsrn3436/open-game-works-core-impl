## done

- `ogw-secure-storage` plugin (module `AuthCore`) for all target platforms of the native plugin table (godot.md:41). Commit f810092
  - android: `client/godot/plugins/ogw-secure-storage/android/` (Godot Android plugin v2 `OgwSecureStorage`). Each item is a file in `Context.getNoBackupFilesDir()/ogw_secure_storage/`, which Auto Backup and device-to-device transfer skip. The file holds AES-256-GCM ciphertext (12-byte nonce + ciphertext + tag, with the item name as associated data) under the Android Keystore key `ogw-secure-storage` (no user authentication, so no OS window). Writes go to a temp file and are renamed into place. Operations run one at a time on a single-thread executor. Dist: `dist/android/addons/ogw-secure-storage/` (`plugin.cfg`, export plugin `ogw_secure_storage_export.gd`, `android/ogw-secure-storage-release.aar`)
  - ios: `ios/` (Godot iOS plugin, engine headers). A generic password Keychain item (service `ogw-secure-storage`, account `<name>`) with `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, not synchronizable, run on a serial dispatch queue. Same logic as macOS without `kSecUseDataProtectionKeychain` and without the entitlement check. Dist: `dist/ios/ios/plugins/ogw-secure-storage/` (`.gdip`, debug and release xcframeworks with an `ios-arm64` slice and an `ios-arm64_x86_64-simulator` slice)
  - windows and linux: `desktop/`. One godot-cpp class `OgwSecureStorage` (`desktop/src/ogw_secure_storage.cpp`) with one operation thread. Operations run in start order. The destructor runs the operations already started, then joins the thread, so a write started right before quit still ends
    - `backend_windows.cpp`: Credential Manager generic credential, target `ogw-secure-storage:<name>`, `CRED_PERSIST_LOCAL_MACHINE` (does not roam). The singleton is always registered
    - `backend_linux.cpp`: Secret Service through libsecret, which is loaded with `dlopen("libsecret-1.so.0")` and has no link dependency. Items are in the default collection, with schema `io.github.wnsrn3436.ogw.SecureStorage` and attribute `name`. It never unlocks: a locked collection or item gives `DENIED`, and no Secret Service or no default collection gives `UNSUPPORTED`. The singleton is registered only when libsecret and all used symbols load
    - Dist: `dist/windows/addons/ogw-secure-storage/windows/libogw-secure-storage.windows.x86_64.dll`, `dist/linux/addons/ogw-secure-storage/linux/libogw-secure-storage.linux.{x86_64,arm64}.so`

## spec proposals

- godot.md:57 says windows is built on a Windows host and linux on a Linux host. This fix built windows on a Mac host with MinGW-w64 (GCC 16.2, posix threads, static runtime) and linux in Debian 11 Docker containers on a Mac host. Proposal: allow the MinGW-w64 cross build for windows and a Linux container for linux, and name the container image, because the glibc of the build sets the lowest Linux the plugin runs on (here symbols up to GLIBC_2.14 for x86_64 and GLIBC_2.17 for arm64). If the rule stays, the windows and linux dists must be rebuilt on those hosts
- godot.md:420 picks DEV token storage only when there is no singleton. With these builds, a dev run or core test on a Windows host always uses Credential Manager, and on a Linux host it uses Secret Service whenever libsecret is installed. On a Linux host with no Secret Service, or a locked or missing default collection (e.g. headless CI), `boot_login` is `Failed`, not DEV token storage. Proposal: decide whether the Linux singleton should also need a reachable, unlocked default collection, or whether DEV runs on Linux should fall back to DEV token storage on `UNSUPPORTED`. I did not add either, because neither is in the spec
- Credential Manager limits a credential blob to `CRED_MAX_CREDENTIAL_BLOB_SIZE` (2560 bytes); a longer item is `FAILED` on Windows. auth-core.md does not bound the storage item size (login token + `linked_providers`). Proposal: state a maximum login token length in server `auth`, or allow splitting the item on Windows
- The native plugin table names platforms but not architectures. Windows arm64 is not built (Homebrew MinGW-w64 has no aarch64 target; llvm-mingw would be needed). A windows arm64 export would have no library, so no singleton, and login token storage is `UNSUPPORTED`. Proposal: state the architectures per platform (windows x86_64 only, or x86_64 and arm64)
