# update core: RealtimeCore M1

## done

- `RealtimeCore` (godot): a room host in `Matching` that started with `join_match` changes to `None` on room updated with `Open`, and the pending `join_match` and `wait_match` are `Cancelled`. `RoomInfo` stays, no transport operation is called, and the next `join_match` of the host is taken
- A host in `Matching` that started with `start_room` is unchanged: it stays `Matching` on room updated with `Open`
- No engine-specific implementation rules document written. `## <engine> build` of `tools/ogw.md` not written

## spec proposals

1. Stale `Open` race. The behavior required by the `host:` line of `### room` cancels a live match in one window, and this change opens that window: before it, the host stayed `Matching` and took match found
   - Cause: the client is `Matching` from `join_match`, but the server changes the room to `Matching` only after `await resolve_members` in `party_match_request` (`server/core/matchmaker/realtime.ts:596`, `:603`). A `ROOM_STATE`(`Open`) caused by a member's `ROOM_JOIN` or `ROOM_LEAVE` before that reaches the host in `Matching`
   - Client side, checked with a temporary test (since removed) that pushed `Open`, then `Matching`, then match found to a host after `join_match`: `join_match` is `Cancelled`, the state stays `None` after `Matching` and after match found, and match found is discarded with one warn log
   - Server side, by reading the code and not run: the party stays in the queue with the room `Matching`, so the other participants of that match wait for a host who does not connect, and a further `join_match` of the host gets `ROOM_BUSY`
   - Implemented as the spec is written, not guarded, because a guard contradicts the current line
   - Proposed text, replacing the `host:` line: "host: on receiving room updated with `RoomStatus` `Open` in the `Matching` it started with `join_match`, after it received room updated with `RoomStatus` `Matching` for that `join_match`, changes to `None`, and the `status` of the pending `join_match` is `Cancelled`. room updated with `RoomStatus` `Open` received before that only changes `RoomInfo`"
   - Evidence is the code above. The alternative of removing the window on the server is not evaluated
2. Scope of the `host:` line. It does not say which `Matching` it covers, while it names only `join_match`. I read it as not covering `start_room`, because `ROOM_START` never changes the room to `Matching` (`realtime.ts:603` is the only such assignment, in `party_match_request`), so an `Open` during `start_room` is an ordinary room change. Proposal 1's text settles this. When proposal 1 is declined, the proposed text is: "host: on receiving room updated with `RoomStatus` `Open` in the `Matching` it started with `join_match`, changes to `None`, and the `status` of the pending `join_match` is `Cancelled`. A host in the `Matching` it started with `start_room` stays `Matching`"
3. `## test` line, after the line that starts "`join_match` of the host calls `start_matching`": "When the host in the `Matching` it started with `join_match` receives room updated with `Open`, the state is `None`, `join_match` is `Cancelled`, `RoomInfo` is the received room, and the next `join_match` calls `start_matching`. The host in the `Matching` it started with `start_room` stays `Matching` on room updated with `Open`"
