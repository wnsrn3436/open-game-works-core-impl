## spec proposals

- `skills/client-core/engines/godot.md`, `QACore` row `font_weight of list_ui`: the row says to read the axes with `get_supported_variation_list()` and the weight class with `get_font_weight()` of the first font. For a `SystemFont` that finds no system font (the browser runtime, and the `qa_font.tres` SystemFont that the QACore tests use in every `list_ui`), `get_supported_variation_list()` is an engine error. `LocalizationCore._weight_axis` already notes this and avoids it. So the implementation reads both from the first text server font of `get_rids()` of the first font, through `TextServer.font_supported_variation_list` and `TextServer.font_get_weight`. For a font with a text server font of its own, this gives the same values. Proposal: write the row with `get_rids()[0]` and these two TextServer calls, as LocalizationCore does
- Same row: it does not say what the first font is when a `FontVariation` has no `base_font`. The implementation uses `ThemeDB.fallback_font`, which the engine draws when no theme supplies a default font. Proposal: add that case to the row, or say that a `FontVariation` without `base_font` gives 0

## unverified

- `total_memory_bytes` > 0 on `android` and `linux`: the `/proc/self/status` `VmRSS` read is not run on this host (macOS), where the native test checks the 0 branch. On `ios` and `windows` only the 0 branch exists, and it is not run either
- `performance.memory` exists only in Chromium-based browsers. The web test ran in the harness browser and passed, so the browser it uses has `performance.memory` or the total check still held. On a page without `performance.memory`, total = heap, and no test runs that case
- The direct-eval name `wasmMemory` was checked in the 4.7.2 web templates only. An engine pin with another Emscripten could rename it. The page memory would then read 0, and the browser test `heap_memory_bytes > 0` would fail and show it
