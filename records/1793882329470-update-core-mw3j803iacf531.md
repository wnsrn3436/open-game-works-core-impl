## done

- module `storage` (commits d469dc5, 7edbe3a, 61d1dc2 on `agent/mw3j803iacf531`, from main b128c7d), made to match the storage spec diff `2e8185b..HEAD`. Much of the diff (the abort rules of `### transaction`, a function that throws, `read_public_state` and `get_user_record` shapes, the advisory lock key, `run_user_changes` leaving out a row and going on) was already on main from earlier rounds. This change adds what was missing:
  - `get_states` (`state.ts`) and `get_user_records` (`rows.ts`), on the module object only (callers `mission`, `block-report`, `public-profile`). Each reads with one query: the ID list goes in as one parameter (`core.ts` `in_id_list`: a PostgreSQL bigint array from `string_to_array`, a SQLite `json_each` array), so 70000 IDs stay one statement on both DBs. `get_states` reads each row as `get_state` does (read conversion written back unless read only) and reads no row outside the list. Duplicate IDs come back once, in ascending order
  - PostgreSQL abort time (`db/pg_worker.ts`, `db/pg_messages.ts`, `db/postgres.ts`): each transaction sets `lock_timeout` and `statement_timeout` (= lock wait limit + `storage.dbAnswerWaitMs`, or + `storage.schemaAnswerWaitMs` in the schema lock transaction) with one `set_config` statement, and the read session sets both the same way. SQLSTATE `57014` is a `lock` DbError (handled as a lock wait over its limit). The adapter's answer limit is now that abort time plus `storage.dbAnswerWaitMs`, and the worker answer bound is 5 steps instead of 4, for the read retry below
  - PostgreSQL read connection: a `read_db` statement that meets a connection failure or a PostgreSQL connection end (`CONN`, `08xxx`, `57Pxx`) on a read connection that was open before the statement runs once more on a new connection. While failing fast it does not retry. A transaction start that finds a free connection ended takes another one for any of those codes (before, only `CONN`)
  - debt D2 (`records/review-debt/storage.json`): `open_tx` gives `NO_FREE_CONNECTION` only when a wait for a free connection used up the lock wait, so `storage.userLockWaitMs` 0 no longer fails every PostgreSQL transaction
  - SQLite (`db/sqlite.ts`): a `string` parameter that holds U+0000 fails the statement with a `sql` DbError, code `22021`, the code PostgreSQL gives
  - `run_savepoint` (`tx.ts`): when the transaction was aborted inside the function, it throws (not a `StorageMisuse`) without a revert or release, whatever the function returned
  - `lock_row` (`tx.ts`): on an aborted transaction every later `lock_game_row` and `replace_game_rows` is `FAILED`, also for a row locked before the abort. Before, a row locked already returned without a check
  - `run_user_changes` (`user_change.ts`): `FAILED` only when the selection or a selected row's `phase` read on `read_db` fails, of any kind (before, only a lock or connection DbError, from anywhere in the row). A row whose phase read failed is not left out. The one error naming the left-out rows is thrown also when a later phase read failed
  - debt D3: already fixed on main by 9e53845 (`body` in `tx.ts` returns `FAILED` for a broken transaction whatever the function returned). The new deadlock tests below cover it again
  - doc comments of the adapter waits (`index.ts` `pg_limits`, `db/types.ts`)

## spec proposals

- `## test` items that put `testing.hold_db` / `testing.until_blocked_by` / `testing.hold_lock_key` in action while a storage call waits (the `pg_terminate_backend` item, the two 0.6 × waits of `lock_game_row`, the deadlock items): a PostgreSQL statement of a transaction blocks the server's thread, and in a storage core test that is also the test's thread. So those `testing` operations, which run on that thread, cannot act during the wait. The tests do that part in another thread's session: the storage test helper `lock_holder` with a delay, and for the terminate item a `DO` block that polls `pg_blocking_pids` as `until_blocked_by` does and then runs the item's `pg_terminate_backend` statement. Proposal: write those items as "another session" instead of naming `testing.hold_db` / `until_blocked_by`, or say that the session runs outside the server's thread
- `replace_game_rows` item: `testing.game_row_lock_id` resolves kinds from the generated contract of the core test data, and storage's tests use their own test contract (`tests/kinds.ts`). So the test passes the same key from `lock_key('game_state', ['boss_game_state', 2])`, the function `game_row_lock_id` ends at. No spec change is needed unless the item is meant to require `game_row_lock_id` itself
