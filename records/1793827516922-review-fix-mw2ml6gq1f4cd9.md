## spec proposals

- R2-1 (still `spec change: yes`): settle the scene holder row of `open-game-works-core/skills/client-core/engines/godot.md:291`. It says that SceneCore writes no property of a node under the holder. It also says that `_process()`/`_physics_process()` do not run under the holder. A node with a `process_mode` of its own (e.g. `PROCESS_MODE_ALWAYS`) breaks the second sentence unless its `process_mode` is written. Godot has no change signal for `process_mode`. So any mechanism that writes nothing and stops such nodes would have to poll every node, and polling leaves a gap between two checks. Proposal, which also settles R1-1 and R2-2:
  1. Allow SceneCore to write `process_mode = PROCESS_MODE_DISABLED` on nodes under the holder with a mode other than `PROCESS_MODE_INHERIT`/`PROCESS_MODE_DISABLED`. It does this in three places: the stage 4 walk, `SceneTree.node_added` until stage 7, and one walk right after `on_preload` returns. At stage 7 it gives the kept mode back to each kept node that is valid and still `PROCESS_MODE_DISABLED`
  2. Add to `scene-core.md` `### scene`: from after `on_preload` returns until stage 7, scene code does not give a node of its own scene a run mode of its own (a mode change in `on_preload`, and the mode of a node added before stage 7, are handled). Add: setting the disabled mode on a node SceneCore stopped is not kept at stage 7. Or choose the opposite rule on purpose
  3. Remove the per-frame stop check (the stop check node and `_watched`). Then R2-2 (per-frame work linear in the node count) and the R1-1 gaps (process priority, a mode given in the middle of a frame) no longer exist, because the spec no longer asks to stop them
- R1-2 (`spec change: yes` on the input line, not fixed): the spec has already settled it, and the input line is stale. The round 1 review set `spec change: yes`, and `open-game-works-core/skills/client-core/modules/scene-core.md:47` and `godot.md:291` were changed afterwards (harness commit `52e5ea3`) to settle it. They now give the `RenderingServer` hiding and say that scene code's `visible` writes are kept. The reviews of rounds 2 and 3 say in `## previous` that it is solved by code alone. But `## previous` has no `spec change` column, so the open finding line keeps the round 1 value. Each round, this agent therefore had to leave it unfixed (see `## review`). Proposal for the harness: let `ogw review` take the `spec change` of a finding from the latest review that judges it, so an open finding line can carry `spec change: no` after the spec has settled it. Then reopen R1-2 with `spec change: no`. The code fix would be to implement the `RenderingServer` hiding of `godot.md:291` in `_hide_if_top`/`_show_hidden` and add the `scene-core.md:170` test (an object directly under the scene root that `on_prepare` hides stays hidden)

## review

- Escalation cause (chain rounds 1 to 3). R1-1 and R2-2 come back after each fix because they are labelled `spec change: no`, but no code fix can close them under the current spec. Scene code can give any node under the holder a `process_mode` of its own at any moment, and Godot sends no signal for that. So stopping such a node before its next callback, as `scene-core.md:47` asks, needs a check of every node at every point where scene code can run. Each fix moved the gap instead of closing it:
  - Round 1 polled from the core node: nodes with a lower priority ran first
  - Round 2 moved the check to the lowest priority: a mode given in the middle of a frame still runs once. It also replaced the walk with the `_watched` set for R2-2: the work per frame is still linear
  - That set brought R3-1: a second start flag, `_watching`, that began after the hiding walk
  
  R3-1 is fixed in code. The remaining gaps and the cost need the spec decision of R2-1 (see `## spec proposals`), which removes the per-frame check altogether. R1-2 remains for a different cause: the stale `spec change: yes` on the input line (see `## spec proposals`)
- R3-1: fixed. `client/godot/core/scene_core/scene_core.gd:335` (`_set_watching(true)` before `_hide_tree(_holder)` at `:336`). Added test `client/godot/core/scene_core/tests/test_scene_holder.gd:139` `test_node_added_by_a_handler_of_the_stage_4_hiding_runs_frames_only_after_stage_7`. It follows the reviewer's run path: `_ready` of `scene_b` connects `Probe.visibility_changed` to a handler that adds a process counter to the scene root. During stage 6 the test sets that counter to `PROCESS_MODE_ALWAYS`. It then checks: the counter is in `_watched`, it has 0 `_process` and 0 `_physics_process` calls before stage 7, and after stage 7 it has its mode back and more than 0 of both. With the `scene_core.gd` of `721fc23` put back, this test failed: the counter was not in the set and had 8 `_process` and 3 `_physics_process` calls before stage 7. With the fix, `test_scene_holder.gd` and the whole module pass
- R2-1: not fixed, `spec change: yes` (see `## spec proposals`)
- R2-2: disputed as a code-only finding. The finding is real, but its `spec change: no` is not. Without a change signal for `process_mode`, a check that stops modes given at any time has to read every node under the holder (see `## spec proposals`, R2-1 point 3). The reviewer's own fix text for round 2 says "Settle with R2-1 a mechanism…". The round 3 review in `## previous` also says "A check that does not touch every node needs the spec decision". The part that code alone can fix, ending the check when the transition ends, was done in round 2
- R1-1: disputed as a code-only finding, for the same reason. The round 3 run path is a mode given in the middle of a frame by a node that processes after the stop check. A node property is set between two checks, and no check point exists between the callbacks of two other nodes. A per-frame polling check cannot stop it. The round 2 reviewer names the cause, "The fix depends on the mapping that R2-1 settles". The cases that code can reach are covered by `test_scene_holder.gd`: a node of the scene resource, nodes `on_preload` adds or changes, a mode given at the start of a frame or physics frame, and a node a hiding handler adds
- R1-2: not fixed, `spec change: yes` from the input line. The line is stale (see `## spec proposals`)
