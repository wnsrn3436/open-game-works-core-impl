## done

- `LocalizationCore` (Godot), `client/godot/core/localization_core/localization_core.gd`
  - `init` reads `LocalizationCore.bodyFontWeight` and `LocalizationCore.headingFontWeight` (an integer is required, as for the other keys).
  - `load_fonts` builds two chains from the font chain:
    - The default font uses the body weight and goes to `default_font` of the theme, which is chosen as before.
    - The heading font uses the heading weight and goes to the theme type variations `HeadingLabel` (base type `Label`), `HeadingButton` (`Button`) and `HeadingRichTextLabel` (`RichTextLabel`). It is set as `font` of the first two and as `normal_font` of the third.
  - A weight above 0 is set as `variation_opentype` `{wght: <weight>}`, only on a font that has a `wght` axis.
    - The chain `FontVariation` itself carries the weight of the first font. Each fallback that takes the weight is a `FontVariation` of that font.
    - A weight of 0, or a font without the axis, keeps the font itself. With both weights at 0, the default font has exactly the structure it had before.

## spec proposals

1. `skills/client-core/engines/godot.md`, `LocalizationCore` row "font weight, text style": say that the chain `FontVariation` itself carries the weight of the first font. Reason: Godot 4.7.2 does not draw the `variation_opentype` of a `FontVariation` that is the `base_font` of another `FontVariation`. Measured with the test font at size 100 and `wght` 800: nested inside the chain, `A` is 60 wide (the default weight); with the weight on the chain itself, 92. A `FontVariation` used as a fallback draws its weight (92). The current wording "each font of the chain wrapped" can be read as nesting the first font, which draws it at its default weight. Proposed wording: "The default font and the heading font are each a `FontVariation` whose `base_font` is the first font of the chain, whose `variation_opentype` holds the weight of that text style when the first font takes it, and whose `fallbacks` are the other fonts of the chain in order, each one that takes the weight wrapped in a `FontVariation` of it".
2. Same row, "only for a font whose `get_supported_variation_list()` has that tag": in the browser runtime, a `SystemFont` that found no system font draws with the default font. Its `get_supported_variation_list()` is an engine error (`Parameter "fd" is null`), reproduced in the web run of the lifecycle test with weights above 0. The implementation reads the axes from `TextServerManager.get_primary_interface().font_supported_variation_list(get_rids()[0])` instead. That is the same RID whenever the font has text server data of its own, and the default font otherwise. Proposed wording: "...only for a font whose first text server font (`get_rids()[0]`) has that tag in `TextServer.font_supported_variation_list`".
3. Same row, "`release` ... removes the three type variations from that theme": a game's project theme can already define `HeadingLabel` and the others (e.g. a heading color). Removing them at `release` would drop the game's own items after a restart. The implementation follows the lifecycle rule ("`release` returns the module to its state before `init`"): it removes only the types the theme did not have before the first `load_fonts`, and gives the others their base type and font item back. Proposed wording: "`release` sets `default_font` of that theme back to its value before the first `load_fonts`, removes the type variations that the theme did not have before it, and gives the ones it had their base type and font back".
