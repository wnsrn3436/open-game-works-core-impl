# update core: auth

## done

Module `auth` (server), commit ab079ed. It is a cherry-pick of bb88c5f from `agent/mvodg74oc6815a`, without that branch's `records/` commits. It applied on main f11d970 with no conflicts and no edits. It matches the `## error` rows of `skills/server-core/modules/auth.md` and the `core_user_created` row of `logging.md` that changed since harness 53674aa.

- `server/core/auth/login.ts`: new `transaction_failed`. It writes one `error` log (request, request ID, user ID, which transaction) and returns `INTERNAL`. These now go through it:
  - the game transaction of `storage.create_user` (`create_user`)
  - the new user `run_user_transaction` (`claim_key`)
  - `run_request_transaction` of the login (`complete_login`, so `Login`, `AutoLogin` and `DevLogin`)
  - the ban login transaction (`ban_login`)
  - `run_request_transaction` of `RefreshToken`

  Before this change, all of these answered `INTERNAL` with no log, because `routing` writes no `error` log when a handler without a token fails.
- A `WITHDRAWN` result of the new user's `run_user_transaction` (in `Login` and `DevLogin`) is now `UNAUTHORIZED`. Before, it was `INTERNAL`.
- A user that an earlier game transaction of the same request made is not cleaned up. It stays.
- `WITHDRAWN` of the ban login transaction was already `UNAUTHORIZED`. A test now covers it.
- `core_user_created` was already sent inside the step 6 transaction, before `core_session_started` (`login_transaction`), so it matches the new `logging.md` row. A test now checks that a user whose login transaction failed has no `core_user_created` and no `core_session_started`.
- `server/core/auth/dev/index.ts`: `DevLogin` uses the same failure results.
- `server/core/auth/deletion.ts` (`POST /account/deletion`):
  - A `FAILED` step 1 `run_game_transaction` now writes an `error` log. It already answered 500 and `[auth_deletion_retry]`.
  - A `FAILED` step 4 `run_user_transaction` and a `FAILED` `remove_user` now write different log messages.
  - The three 500 causes (the two above and the `read_db` lookup failure) now share one outcome that carries the cause it logs. This keeps `deletion_post` within the lint complexity limit.
- `server/core/auth/tests/transaction-failure.test.ts` (new). Inside the target transaction, each test throws the lock-failure `DbError` that the DB adapter throws. Storage then rolls back and returns a real `FAILED`. The tests check:
  - each `FAILED` row gives `INTERNAL` (or 500 and `[auth_deletion_retry]`, the same page as another retry) and exactly one `error` log.
  - `Login`: when `create_user` fails, no user is made. When the link or login transaction fails, the new user stays (not withdrawn, unlinked, no login token, no core events), and the account links to a new user on the next `Login`.
  - `AutoLogin`, `RefreshToken`, the ban login: login token rows stay unchanged, and the next request succeeds (or is `BANNED`).
  - `DevLogin`: each of its three transactions.
  - deletion step 1 and step 4 (`code` and `google`): nothing is deleted, no attempt is counted, and the same form deletes afterwards.
  - `WITHDRAWN` of the ban login, for `Login` and `AutoLogin`: `UNAUTHORIZED`, no `ban`, no `error` log.
