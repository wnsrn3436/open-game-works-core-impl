# update core: matchmaker

## done

- `matchmaker` (server):
  - result decision (`judge.ts`): forfeiter, complete record, final decision (complete or at `deadline_at`); before that only the `CONFIRMED` condition decides. `ServerReplay` replays only an `input_log` with c ≥ 2 and 2c > k (k: participants that are not forfeiters), 2c > r in the final decision. `FORFEIT` when the final decision has a forfeiter and a report of a participant that is not one, else `MISMATCH`. `MISMATCH` is void
  - decision points: after each saved report (`ReportMatchResult`), in a separate game transaction started with `storage.after_commit` after the `left_at` write commits (not retried; its failure leaves an error log), and at `deadline_at` (step 5 of `ReportMatchResult` and job `matchmaker_sweep`). `replay_match` failing in the decision after a leave or in the sweep is `MISMATCH` with an `error` log; in `ReportMatchResult` it is still `INTERNAL`
  - hook `apply_match_forfeit`; the match record input has `status` (`MatchJudgeStatus`) and `participants[].ended_at`
  - integrity (`### integrity`): table `matchmaker_integrity` (key `(user_id, match_id)`, expiry `expires_at`, personal data column `user_id`, index `(kind, at)`), `Disagree`/`Forfeit`/`Missing`, integrity locks `(user_id, "")` in ascending user ID after the match row lock (a `FAILED` lock fails the judging transaction), flag count, and the `warn` `core` log `match integrity flag` registered with `storage.on_commit` when the count equals the `matchmaker.flag*Count` key. A record with an event is kept for the larger of `recordRetentionMs` and `flagWindowMs` (new nullable match column `integrity`)
  - admin operations `list_match_flags` and `get_match` (role `read`, `admin.ts`)
  - `MATCH_LEAVE` `forfeit`: `ENDED` writes `ended_at` (new nullable participant column), `LEFT` writes `left_at`. A failed `LEFT` write is retried after g(a) up to `matchmaker.applyRetryMaxAttempts` attempts, behind the per-match order; error log at the first failure and at the drop. `DISCONNECTED`, `ENDED`, `REJOINED` are not retried
  - a `MATCH_LEAVE` that arrived before the close of its connection and whose handling had not started is handled before that connection close (`realtime.ts`, `leave_before_close`)
  - `HELLO`: `platform` must be empty or `validation.is_platform`; `game-update.is_below_min_version` gives `CLOSE`(`APP_UPDATE_REQUIRED`) for a non-empty `client_version`
  - match `seed` from `storage.make_seed('match')`; `new_seed()` removed
  - `matchmaker_participant` registered with personal data user column `user_id`
- Other module changed because matchmaker's change needs it: `server/core/routing/spec_tables.ts` `MODULE_ADMIN_OPERATIONS` gets `'matchmaker': ['list_match_flags', 'get_match']`. Without it routing does not collect the two operations, and admin-api answers 404

- Last `ogw core test server matchmaker rating routing testing`: all pass on SQLite and PostgreSQL. `ogw code check core` after it: type check, lint, dependency and secret pass
- Flaky `rooms.test.ts` "party > answers ROOM_START and a host MATCH_REQUEST with ROOM_BUSY … go on after that member MATCH_LEAVE": the cause was in the test. After `MATCH_LEAVE` it read the committed match record at once. The participant change of the leave is a game transaction of its own, and the frame handling does not wait for it (`### connection`). So under load the read could come before the commit (`expected … length of 1 but got 2`). I confirmed this by holding the next `run_game_transaction` while the leave was handled: the run failed the same way, with the same message, on both SQLite and PostgreSQL. 25 runs in a row without the hold all passed. The fix: the test now waits until the write has committed (`until_participants`) before it checks. It also checks `ended_at`, since that `MATCH_LEAVE` has `forfeit` `false`. I found no record of the "ROOM_BUSY after MATCH_LEAVE" variant (the only record, `records/1794138877224-update-core-mw7rypm0886bd4.md`, names the length failure) and could not reproduce it. Nothing was raised and no retry was added

## spec proposals

- `### connection` / `### result decision`: the decision transaction after a `left_at` write is not said to be at `deadline_at` when it runs after `deadline_at` (before job `matchmaker_sweep` judged the record). The implementation treats it as the final decision at `deadline_at` when `deadline_at` ≤ `clock_now` (so it gives `Missing`), as step 5 of `ReportMatchResult` does. Proposal: say so
- `## test` "A `MATCH_LEAVE` with `forfeit` `true` and the WebSocket close of its connection right after it, both arriving while the server instance waits in a DB call held by `testing.hold_lock_key` …": with a test server, the test runs on the same thread as the server instance, so it cannot send frames while that thread is blocked in a DB wait. The test I wrote makes the connection's frame handling wait instead: a `MATCH_REQUEST` waits in its held `prepare_match_request` transaction, and the `MATCH_LEAVE` and the close arrive behind it. It runs on both DBs. Proposal: write the item as "while the frame handling of that connection waits", or name a peer-process setup
- `list_match_flags`: `count` is written as a JSON number. The spec does not give its field type (it is not an `int64`)
