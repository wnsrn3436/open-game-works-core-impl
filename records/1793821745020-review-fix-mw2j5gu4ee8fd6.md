## spec proposals

- R1-1 (spec change: yes, not fixed): `guild` `### tables` judges the `guild_cooldown` row against request time (`is_reached_strict`), while `storage` `### expiry` treats a row whose expiry column is at or before `clock_now` as not existing and `storage_sweep` deletes it by `clock_now`. With a DEV time offset, or simply between a request and a later sweep, `JoinGuild`/`CreateGuild` give `GUILD_COOLDOWN` before the sweep and succeed after it at the same request time. Proposal: one time base for this table in the specs. Recommended: exclude `guild_cooldown` from the storage expiry rule (no expiry column; guild deletes the row itself when it judges it reached, and `remove_user` already deletes it), because the cooldown is a gameplay-facing time that the DEV time offset must move, as the other request-time judgements of guild do. The alternative is to write and judge `ends_at` with `server-time.clock_now`, which makes the cooldown ignore the DEV cheat offset
