# VirtualPadCore review fix (round 4)

## done

- Module `VirtualPadCore` (Godot), `client/godot/core/virtual_pad_core/virtual_pad_core.gd`:
  - Pointer ownership now follows `### pointer ownership` (R3-1). The 32-entry `_area_pointers` table (`_AREA_POINTER_SLOTS`, `_add_area_pointer`, `_remove_area_pointer`) is gone. While `ACTIVE`, an element accepts every touch press on it, and accepts moves and a release only for the pointer it holds (`element.pointer_id`). There is no limit on area presses any more, and the pointer path no longer tracks pointers that no element holds.
  - `HIDDEN` no longer sets `_pad.visible = false` (R4-1). `_apply_state` hides the drawing with `RenderingServer.canvas_item_set_visible(_pad.get_canvas_item(), …)`, so the element `Control`s stay visible to the engine GUI. The engine then keeps the mouse focus and touch focus that an element holds, and the later moves and release of that pointer reach no UI element outside the virtual pad.
- Core tests:
  - New `tests/test_ui_below.gd`, which puts a real `Button` (`VirtualPadTestButton`) on the `SceneUI` layer and counts its touch and mouse input and its `pressed` signal. It covers R4-2 (a)–(c) and R4-1.
  - New `tests/test_render_state.gd`, a render test: the pad is drawn when `Active` and `Inactive` and not drawn when `Hidden`, checked by window pixels.
  - `test_pointer.gd::test_forty_pointers_in_one_button_area_leave_the_joystick_free` is the test item at spec :218 (R3-1).
  - `test_state.gd::test_popup_makes_it_inactive` now uses a modal popup that covers the screen and counts its input (R4-2 (d)).
  - Support: `VirtualPadTestControl` counts mouse input too (field renamed from `touches` to `inputs`). New `VirtualPadTestPopup` and `VirtualPadTestButton`, and popups `test_popup_side.tscn` (not modal, area (800, 0)-(1300, 400)) and `test_popup_cover.tscn` (modal, full screen). New helpers in `virtual_pad_test_case.gd`: `mouse_button`, `make_scene_button`, `restart_modules`, `counting_popup` and `open_popup(key)`.
  - In `after_each`, the test base now releases the touches that a test left pressed. The engine makes mouse input only from the first touch pressed while no other touch makes it. So a touch 0 left pressed by `test_input_device_change_hides_and_releases` stopped the next test's touch 0 from making a mouse press, and its mouse moves went to the popup by hit test. A probe reproduced this: the same steps passed when run alone and failed only after that test.
- Runs:
  - `ogw core test godot VirtualPadCore BootstrapCore QACore UnitTestCore`: headless 402/402 passed. The render pass was not run because the macOS screen is locked.
  - The same run with `--web`: every module passed.
  - `ogw code check core`: type check, lint, dependency and secret all pass.
  - The R4-1 test fails on the old code: with `_pad.visible = …` restored temporarily, `test_device_change_while_held_keeps_the_pointer_from_the_button_below` failed with the button getting 1 input. The fix was then restored.
- No engine-specific implementation rules document was written. `## <engine> build` of `tools/ogw.md` was not written.

## spec proposals

- input-block-core.md :106 says "A UI element that is not visible … lets nothing pass". With this fix, the element `Control`s of a `Hidden` virtual pad are visible to the engine and only their drawing is off. So under a block whose pass list has a virtual pad element, a touch press in that element's area while `Hidden` now passes the block stage. Before, the element was invisible and the press was discarded. That touch then switches the device to `Touch`, the pad becomes `Active` before the UI stage, and the element takes the pointer. Proposal: state in virtual-pad-core.md, or in the godot.md row of `VirtualPadCore`, whether a `Hidden` element counts as "visible" for a block pass list. I recommend that it does, because the first touch on a passed joystick then works. No test covers this case either way.

## review

- R4-1: fixed.
  - Code: `client/godot/core/virtual_pad_core/virtual_pad_core.gd:445` (`_apply_state` hides the drawing in the rendering server and keeps the controls visible).
  - Test: `tests/test_ui_below.gd::test_device_change_while_held_keeps_the_pointer_from_the_button_below`. It presses a touch in the `fire` area over a `SceneUI` button, changes the device to `Gamepad`, moves inside that button and releases, then asserts 0 inputs and 0 clicks on the button. It fails on the old code.
  - Test: `tests/test_render_state.gd::test_hidden_draws_nothing_and_active_and_inactive_draw` checks "does not draw" by pixels.
- R4-2: fixed.
  - (a) `test_ui_below.gd::test_keyboard_mouse_click_reaches_the_button_below` and `::test_touch_under_a_side_popup_reaches_the_button_below`.
  - (b) `::test_touch_moved_out_of_a_button_area_does_not_reach_the_button_below` (released outside the area, and released back over the button) and `::test_popup_between_press_and_release_keeps_the_pointer_from_the_ui`.
  - (c) `::test_touch_with_the_gamepad_device_clicks_the_button_below_and_presses_the_action`.
  - (d) `test_state.gd::test_popup_makes_it_inactive` with `POPUP_COVER`: the popup gets neither the moves nor the release. The side popup case is also in `test_popup_between_press_and_release_keeps_the_pointer_from_the_ui`.
  - `VirtualPadTestControl` now counts `InputEventMouse` (`tests/support/virtual_pad_test_control.gd:9`), so `test_second_pointer_in_an_owned_element_changes_nothing` also checks for mouse input.
- R3-1: fixed.
  - Code: `virtual_pad_core.gd:494-513` (`_on_element_input` accepts every press in an area while `ACTIVE`, and accepts moves and a release only for `element.pointer_id`). The slot table was removed.
  - Test: `tests/test_pointer.gd::test_forty_pointers_in_one_button_area_leave_the_joystick_free`. With `InputCore.maxJudgePointers` 50 and 40 pointers in `fire`, a `Fixed` joystick press at 0.5 times the radius gives (0.5, 0), and the 40 releases give no `TapEvent`.

## unverified

- The render pass, and with it `test_render_state.gd`, was not run because the macOS screen is locked. "Hidden draws nothing" is therefore unchecked on a real window. `RenderingServer` has no getter for canvas item visibility, so the headless pass cannot check it.
- On-device touch was not checked. The engine's touch focus surviving `INACTIVE` and `HIDDEN` was checked only through the counts of the headless tests.
- Engine behavior used by the fix was not read in the Godot 4.7.2 source: the engine keeps an element's mouse focus and touch focus while its `mouse_filter` is `IGNORE` and it is visible, and it keeps it when the pad's canvas item is hidden in the rendering server. Both were observed only through the tests above.
