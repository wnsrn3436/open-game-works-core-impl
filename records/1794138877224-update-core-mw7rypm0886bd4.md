# update core: auth

## done

- `auth` (server):
  - login token expiry: `auth.loginTokenIdleTtlMs` is read in `server/core/auth/settings.ts`. `login_token_expired` in `server/core/auth/login.ts` judges the row that `AutoLogin` and `RefreshToken` first read with `storage.read_db`. A token is expired only when the user has an `auth_social_link` row (read through the same `read_db` handle) and `last_used_at` + TTL ≤ `server-time.user_now`. An expired token is `UNAUTHORIZED` with no `security` log and no new row. The existing login token rotation renews `last_used_at`
  - core rpc `LogoutOtherDevices` (`logout_other_devices` in `server/core/auth/account.ts`): inside the request transaction it calls `session.check_current(user, ctx.session_id)` first. When that is not `pass`, it returns that failure (`SESSION_REPLACED`/`UNAUTHORIZED`) and deletes nothing. Otherwise it deletes the user's login token rows whose `session_id` differs from the request's session (`delete_login_tokens_of_other_sessions` in `tables.ts`). It is exported from `index.ts`
  - admin operation `revoke_login_tokens` (`ops`, `user_target` `user_id`) in `server/core/auth/admin.ts`: it returns `conflict` when the user has no `auth_social_link` row. Otherwise it deletes every login token row of the user (`delete_login_tokens_of_user`) and calls `session.end_session`. `not_found` and the audit log for a missing or withdrawn user come from `admin-api`'s `user_target` handling
- Caller in another module that had to follow the change: `routing` `server/core/routing/spec_tables.ts`. `LogoutOtherDevices` is added to `MODULE_CORE_RPCS.auth` and `revoke_login_tokens` to `MODULE_ADMIN_OPERATIONS.auth`, without which `routing` does not collect them. The mock auth module object in the `routing` test `server/core/routing/tests/collection.test.ts` gets the same two names
- session spec change: it needed no session code, because `end_session` already exists and `revoke_login_tokens` calls it. The session `## test` item "after a successful `auth.revoke_login_tokens` ... a request of that session is `UNAUTHORIZED`; for a user without a link it is `conflict` and changes nothing" is tested in auth's tests, because `session` cannot depend on `auth`
- admin-api operation table row: it needed no admin-api code. The role comes from the operation object, and collection goes through `routing`'s table above
- Tests:
  - new `server/core/auth/tests/login-token-expiry.test.ts`: success 1ms before the expiry; at the expiry both calls are `UNAUTHORIZED` with no security log and no new row; renewal by `RefreshToken` at t; social `Login` after the expiry gives the same user ID and a token that `AutoLogin` accepts; a guest's token does not expire for `AutoLogin` or `RefreshToken`
  - new `server/core/auth/tests/logout-other-devices.test.ts`: the A/B/C devices case, including both the requested and the next token of B after its `AutoLogin`; guest and DevLogin accounts; the race with an `AutoLogin` of A held after step 5 (`SESSION_REPLACED`, rows unchanged, A stays current, a copy of A's token is valid after `LogoutOtherDevices` of A); `revoke_login_tokens` success, `409 conflict` for a guest, `404` for a withdrawn or nonexistent user with an audit log
  - the existing test in `login.test.ts` was renamed so that it says it covers a user without an `auth_social_link` row
