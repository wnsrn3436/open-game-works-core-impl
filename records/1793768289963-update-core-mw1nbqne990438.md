## spec proposals

1. `### room` of `realtime-core.md` does not write `close` on the `Open` that ends a `Matching`, in the host line and the non-host member line. `poll` in the same spec says "the `close` of that change has already left a match found of the same `poll`", and `## test` asks for one `MATCH_LEAVE`, which only that `close` can send. The implementation follows those two lines. Proposal: add "calls `close`" to both `Open` sentences of `### room`, so the spec states it. The implementation changed before this spec line did, so the lead agent decides whether the wording goes in.
2. A non-host member that gets `Matching` after the change to `None` in the same `poll` still takes the match found: `## test` keeps "match failed, room updated(`Open`), room updated(`Matching`) and match found in one `poll` end in `Connecting`", and the state is no longer `None` when match found is handled. On the real transport the `close` of that change has already left the match, so `connect_peer` has no peer to connect, and the member should go to `Failed` at the connect time limit. This is the defect item 1 of the input removes for `None`. It was already there for match failed, and item 2 above extends it to room updated(`Open`), room updated(`Matching`), match found without match failed, which reached the match before this change. Proposal: discard a match found after any `close` in the same `poll`, whatever the state, and change that `## test` line to expect `MATCH_LEAVE` and no `Connecting`. Not changed here, because the spec line keeps it. This comes from reading the code, not from a run on the real transport.
