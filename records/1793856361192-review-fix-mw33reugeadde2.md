## spec proposals

- `block-report` `## API`: write the U+0000 rule in the `ref` and `evidence` lines, e.g. "`ref` ... At most `block-report.maxRefBytes` bytes and holds no U+0000", and the same for `evidence`. The code rejects them now because PostgreSQL rejects U+0000 in a text value while SQLite stores it, so the report row write cannot give the same result in both DBs (`storage` `## behavior`: "Queries use only SQL that gives the same result in both DBs"). A `## test` item: "`ReportUser` with a `ref` holding U+0000 is `INVALID_REQUEST`, and `add_report` with a `ref` or `evidence` holding U+0000 is `INVALID_INPUT`, with no report row, on both DBs". The same cause can apply to other modules that write a `string` column from a request string that only `max_len` checks. A general rule in `storage` or in the contract string validator (`validation` `### validator`) would remove it at its source for all modules.
- For R1-2 (see `## review`): either add `block-report` to the `caller` of `storage.get_user_records`, and let `BlockUser` step 4 judge the withdrawal state of all `blocked_id` values with one `get_user_records` call per group of at most `public-profile.maxRequestCount` IDs, or add to `public-profile` an operation that gives `is_active_user` for a list of user IDs (caller `block-report`) built on `storage.get_user_records`. Also: `storage.get_user_records` is in the `storage` spec (`## API`, `## test`) but has no implementation in `server/core/storage/`, and `public-profile.get_public_profiles` reads one `get_user_record` per user ID (server/core/public-profile/index.ts:210), not `get_user_records` per group as `public-profile` `## behavior` says. Those belong to `storage` and `public-profile`.
