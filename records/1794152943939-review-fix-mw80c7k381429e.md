# review fix matchmaker round 1

## done

- `matchmaker` (server/core/matchmaker/realtime.ts): at a connection close, the `MATCH_LEAVE` frames that arrived before the close and whose handling had not started now go on the frame chain of that connection. Each starts after the previous frame's handling ends, and the close handling (queue and room removal, `p2p-signaling.connection_closed`) runs after them (`drop`, realtime.ts:332; `connection_close`, realtime.ts:368). `client.closed` is still set at the close, so a frame being handled sees the close at once (e.g. step 4 of the `MATCH_REQUEST` processing order).
- With no such `MATCH_LEAVE` frame waiting, the close is still handled at once, as before. This is required by matchmaker.md:116 and :413 (a new connection authenticates while `prepare_match_request` of the previous connection waits), :179 (a close during match creation) and :471 (a host that left while its own `ROOM_START` still makes the match). The existing tests of those items (matching.test.ts:522, rooms.test.ts:982, :995) failed when every close waited behind the frame chain. So I did not take that part of the review's suggested fix.
- `HELLO` (realtime.ts:440): when the close of the replaced connection waits behind its frame chain, `HELLO_ACK` of the new connection waits for that close handling, so that "handles that connection close before sending `HELLO_ACK`" (matchmaker.md:116) still holds. It also stops before authenticating if the new connection closed during that wait.
- No engine-specific implementation rules document. `## <engine> build` of `tools/ogw.md` was not written.
- Last `ogw core test server matchmaker rating routing testing` (the modules `ogw core dependents matchmaker` lists on the server side) on commit 89e01892: all pass on SQLite and PostgreSQL. `ogw code check core`: type check, lint, dependency and secret pass.

## spec proposals

- matchmaker.md:122 and :116 together leave open which parts of a connection close wait behind the frame being handled. The implementation handles the close at once unless `MATCH_LEAVE` frames that arrived before it are waiting. Then those frames and the whole close handling (and `HELLO_ACK` of a replacing connection) come after the frame being handled. Proposal: state this in `### connection`, e.g. "When `MATCH_LEAVE` frames that arrived before the close wait behind the frame being handled, the connection close is handled after them, and `HELLO_ACK` of a new connection of that user waits for it; otherwise the connection close is handled at the close."

## review

  - server/core/matchmaker/tests/forfeit.test.ts:604 now checks that, while the hold is in place, the other participant gets no `PEER_LEFT` and `left_at` of index 1 is 0. After `held.open()` it checks that `left_at` is written, `disconnected_at` is 0 and `PEER_LEFT` arrives.
  - forfeit.test.ts:628 (new): a `MATCH_LEAVE` waits behind a held `MATCH_REQUEST` and a new connection of the same user sends `HELLO`. The replaced connection gets `CLOSE`(`SESSION_REPLACED`), and while the hold is in place there is no `PEER_LEFT`, no `HELLO_ACK` and `left_at` is 0. After the hold, `HELLO_ACK` arrives, `left_at` is written and `disconnected_at` stays 0.
  - Both tests fail on the code before the fix (`expected [ 12 ] to not include 12`: the old code sent `PEER_LEFT` during the wait) on SQLite and PostgreSQL, and pass after it.

## unverified
