## review

- R3-1: fixed. `server/core/auth/tests/withdraw.test.ts` describe `Withdraw while another transaction commits a friend link row (PostgreSQL)`, test `a friend link row of U and B that commits while Withdraw of U waits for the friend_count row of A makes Withdraw INTERNAL with one error log of auth`. It follows auth.md `## test`. The test holds A's `friend_count` lock with `testing.hold_lock_key(testing.game_row_lock_id('friend_count', [A]))` and sends `Withdraw` of U, who is A's friend. It waits with `testing.until_blocked_by`, then a `testing.hold_db` inserts the U–B link rows and runs `COMMIT`, and the holder is released. It asserts that `Withdraw` is `INTERNAL`, that the peer's `error` log entries are exactly one `withdrawal rolled back: a remove_user is CHANGED` with U's user ID and `core/Withdraw`, and that U has no `withdrawn_at`. The `Withdraw` runs on a `testing.start_peer_process` peer (`server/core/auth/tests/peer.ts`). On the test server's own instance, the synchronous DB wait would block the test thread, so `hold_db` and the release could not run. The peer's log lines go nowhere, so the peer's `register` wraps `logging.write`, which `routing` and `auth` call, to keep its `error` entries for the test. Checked: the test fails when the second-read `CHANGED` check of `friend.remove_user` is removed (`Withdraw` becomes 0). A temporary failing sentinel confirmed that the test runs in the PostgreSQL run
- R3-2: fixed. `server/core/auth/tests/withdraw.test.ts` test `a friend.remove_user CHANGED makes every withdrawal fail and roll back, and Withdraw and ConfirmAge leave the error log of auth`, using the shared `withdrawals_roll_back` with the hold `link_before_lock`. Before the real `friend.remove_user` locks the user's own `friend_count` row, the hold inserts a link row with another user in the same transaction (the friend `insert_before_lock` pattern), so `remove_user` gives `CHANGED`. It runs on SQLite and PostgreSQL and checks the following:
  - `Withdraw` and `ConfirmAge` below the minimum age are `INTERNAL`, and they leave exactly the two `auth` `error` logs (`core/Withdraw`, `core/ConfirmAge`)
  - `withdraw_user` is 500
  - `POST /account/deletion` is 500 with `[auth_deletion_retry]`
  - `auth_guest_sweep` keeps the guest, leaves the guest cleanup `error` log and no `inactive guest withdrawn` audit
  - neither user has `withdrawn_at`, the member's UserState and social link rows are unchanged, and there is no `revoke`

  Checked by mutation, one revert at a time, each failing on both DBs:
  - restoring `=== 'FAILED'` in `admin.ts:31` (withdraw_user 200)
  - restoring it in `deletion.ts:206` (page 200)
  - restoring it in `guest_sweep.ts:24` (an `inactive guest withdrawn` audit line). The first version of the test did not catch this revert: the partial commit stops before `storage.delete_user`, so `withdrawn_at` stays null. The sweep log assertion was added to `withdrawals_roll_back` for this reason
