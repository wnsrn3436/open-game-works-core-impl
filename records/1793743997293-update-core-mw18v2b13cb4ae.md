## spec proposals

1. `realtime-core.md:107` does not say what a room updated kept after `None` does beyond changing `RoomInfo` and publishing `RoomChangedEvent`. I read it as an ordinary room updated, so `:184` also applies: a non-host member that receives room updated with `Matching` there changes to `Matching` and publishes `RoomMatchStartedEvent`. Since the state is then not `None`, the notifications after it in that `poll` are handled, the same as when a retry leaves `None`. The alternative is that the member stays `None` and a match found in that `poll` is discarded, so the other participants wait for that member. Proposed text, added to `:107`: "A room updated handled this way is handled as in `### room`. When it changes `MatchState` from `None`, the notifications after it are handled"
2. A stale `Matching` can still end a later `join_match`. Sequence, by reading the code and not run: the host calls `join_match`, then `leave`, then `join_match` again while `ROOM_STATE`(`Matching`) and `ROOM_STATE`(`Open`) of the first entry are in flight. `p2p_realtime_transport.gd` `close` keeps the socket in a room, so both frames arrive. The client counts that `Matching` for the second `join_match`, and the `Open` then gives `Cancelled` while the server queues the second entry. `ROOM_STATE` does not identify the entry, so the client cannot tell them apart under the current contract. Line `:183` says "for that `join_match`", which the code can only do approximately. Fixing this needs a contract change (e.g. an entry number in `MATCH_REQUEST` and `ROOM_STATE`) or a server change. No evidence on how often it happens, and I do not recommend either without a decision
