## spec proposals

- `skills/client-core/modules/virtual-pad-core.md:226`, the second sentence of the test item: "When the input device changes to `Gamepad` while a touch pressed in a button area is held, the elements become not visible UI elements when that touch is released". This cannot happen as written. The touch release is itself touch input, and `InputCore` uses it for device detection (input-core.md:95 and :116: even a discarded input is used for device detection, and touch is `Touch`). So the release makes the device `Touch` again, the state becomes `Active` (virtual-pad-core.md `### state`), and `Active` elements are drawn and visible. Recommendation: reword the item so that the state stays `Hidden` through the release. e.g. "When touch support is turned off with `set_test_touch_support(false)` while a touch pressed in a button area is held, the elements stay visible UI elements until that touch is released and are not visible UI elements after the release". The core tests check that form now (`test_state.gd::test_hidden_elements_become_not_visible_after_the_held_touch_is_released`, `test_ui_below.gd::test_hidden_elements_keep_the_held_touch_from_the_button_below_and_then_let_it_through`). They also check the literal `Gamepad` wording as closely as it can be checked: the device is set back to `Gamepad` right after the release (`test_state.gd::test_elements_become_not_visible_when_the_held_touch_is_released`)
- Possible addition to virtual-pad-core.md:38: after an input cancel, a pointer pressed before the cancel no longer counts as "a pointer whose press was consumed ... still pressed". `InputCore` discards that pointer's later moves and release (input-core.md block stage), so it reaches no UI element either way. The code does this (`_check_cancel` → `_forget_consumed`) so that a pointer whose release never comes (e.g. app focus loss) cannot keep a `Hidden` pad visible to the GUI. The spec only says the elements are not visible while no consumed pointer is pressed, and says nothing about the time while one is pressed, so this is within the current spec. Writing it down would make it explicit

## unverified

- Only the Godot headless runs checked the visibility, through `is_visible_in_tree()`, which is the mapping godot.md:397 gives for a visible UI element. `QACore.list_ui` and the `InputBlockCore` pass list were not called directly in the new tests; both read `is_visible_in_tree()` (`qa_query.gd:214`, `input_block_core.gd:485`)
- `_on_input` assumes the `VirtualPadCore` node comes after the `InputCore` node in the root, so its `_input` runs first and sees a release before `InputCore` can discard it. This holds because `VirtualPadCore` depends on `InputCore` and is initialized after it. If `InputCore` were restarted alone while `VirtualPadCore` stays, a release that `InputCore` discards could be missed. `InputCore` discards a release only when the pointer's press never passed the block stage (so it was never consumed by an element), after an input cancel (the tracking is cleared then), or for the DEV debug handler. No test covers a lone `InputCore` restart
- It was not checked on a device whether a real platform sends a touch release when the app loses focus. The cancel path covers a missing release, because a focus loss cancels input in `InputCore`
